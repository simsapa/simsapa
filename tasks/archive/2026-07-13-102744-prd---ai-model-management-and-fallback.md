# PRD: AI Model Management and Fallback

## 1. Introduction / Overview

Simsapa's AI features (Gloss tab AI translation, Gloss AI word selection, Prompts
tab chat) use models from providers configured in a bundled `assets/providers.json`.
Today the model ID lists are maintained largely by hand: the user adds/removes and
enables model IDs one by one in `ModelsDialog.qml`, and the Gloss "Word
Selection..." dialog has its own separate model picker. When a request fails
(rate limit, overload), the retry logic in `GlossTab.qml` blindly re-tries the
same model up to 5 times and gives up on rate limits; error messages are shown
as raw response text / JSON.

This feature refactors model management around two principles:

1. **Model lists maintain themselves.** A shared update procedure (used by both
   the CLI and a new in-app "Update Model Lists" button) refreshes each
   provider's model ID list from published data — primarily the
   [models.dev](https://models.dev/api.json) aggregator, plus a provider's own
   public API where it is better (see §7). The bundled `providers.json` is
   generated by this procedure, with a reasonable default model auto-enabled
   per provider (best of the available free models, chosen heuristically).

2. **Model *selection* at request time is automatic.** Two new global lists in
   `ModelsDialog.qml` — an ordered **"Fallback sequence"** and a
   **"Parallel prompts"** list — govern which enabled models are used. On errors,
   the app first *falls back* to the next model in the sequence, and only after
   the sequence is exhausted does it *re-try*: "First we auto-fallback, then we
   re-try the model requests." The Gloss Word Selection dialog no longer needs
   its own model picker.

The goal: the user enables providers/models once (or accepts the defaults) and
the app takes care of choosing, falling back, retrying, and keeping the lists
current.

## 2. Goals

1. Eliminate routine manual curation of model ID lists (adding new / removing
   obsolete model IDs).
2. One shared Rust procedure for refreshing model lists, used by the CLI
   (regenerating the bundled `providers.json`) and by the in-app
   "Update Model Lists" button (background, non-blocking).
3. Bundled `providers.json` ships with one sensible free model auto-enabled per
   provider, picked by a metadata heuristic (not hand-curated).
4. A single, user-orderable **Fallback sequence** drives all sequential AI
   requests (Gloss translate sequential mode, Word Selection, Prompts sequential
   mode); a **Parallel prompts** list drives all parallel AI requests.
5. Fallback/retry logic moves out of QML into one shared Rust implementation
   used by all three AI features.
6. Recognizable API errors (rate limit, overload, invalid key, quota) are shown
   as clear human-readable messages; raw JSON display remains the fallback.

## 3. User Stories

- **US-1:** As a user, I want new models (e.g. a newly released Gemini flash) to
  appear in my model lists after clicking "Update Model Lists", without me
  reading provider changelogs and typing IDs.
- **US-2:** As a user, I want obsolete/retired model IDs cleaned up
  automatically so my requests do not fail with "model not found".
- **US-3:** As a first-time user, I want a working free model already enabled
  after I paste in a provider API key, so AI translation works immediately.
- **US-4:** As a user, when a model is rate limited or the provider is
  overloaded, I want the app to automatically try my next preferred model
  instead of failing, in an order I control.
- **US-5:** As a user, I want to choose per feature whether AI requests run in
  parallel across models (comparing outputs) or sequentially with retries
  (one good answer, cheaply).
- **US-6:** As a user, when a request fails I want to see *why* in plain words
  ("Rate limited by Gemini — retrying with Mistral…"), not a JSON blob.
- **US-7:** As a user, I can still manually add a niche model ID (e.g. a
  HuggingFace model) and it must survive list updates.

## 4. Functional Requirements

### A. Shared model-list update procedure (Rust, `backend` crate)

- **FR-A1.** There must be a single Rust function (in the `backend` crate so
  both `cli` and `bridges` can call it) that takes the current providers
  configuration and returns an updated one, refreshing each supported
  provider's model ID list.
- **FR-A2.** The **primary source is models.dev** (`https://models.dev/api.json`,
  one fetch per run) for all providers it covers. Verified provider-key mapping:
  Gemini → `google`, OpenRouter → `openrouter`, Mistral → `mistral`,
  Anthropic → `anthropic`, OpenAI → `openai`, DeepSeek → `deepseek`,
  xAI → `xai`, Perplexity → `perplexity`, NvidiaNim → `nvidia`,
  HuggingFace → `huggingface`.
- **FR-A3.** **SambaNova is absent from models.dev** and must keep using its
  native endpoint (`https://api.sambanova.ai/v1/models` — verified live to
  respond 200 without auth; note the existing `fetch_sambanova` in
  `cli/src/update_provider_models.rs` requires a bearer key unnecessarily —
  do **not** port that `require_key`). **OpenRouter** should use its native keyless endpoint
  (`https://openrouter.ai/api/v1/models`) as the authoritative source because it
  is richer than models.dev (includes non-`:free` variants and live pricing);
  keep the existing `:free`-suffix filter for OpenRouter. All other providers
  use models.dev only — no API keys are required by the update procedure at all
  (this replaces the key-gated native fetchers in
  `cli/src/update_provider_models.rs`).
- **FR-A4.** Only chat-capable text models may be listed. Reuse the modality
  check (`modalities.input`/`output` must contain `"text"`) plus the denylist
  filtering already established in `fetch-models.sh` / the existing per-provider
  filters (no embed/rerank/guard/whisper/tts/image/ocr/moderation models).
- **FR-A5.** **HuggingFace model lists are not auto-updated** (too many models);
  its user-added entries are preserved untouched.
- **FR-A6. Merge semantics (per provider):**
  - Models fetched upstream that are not in the current list are appended,
    `enabled: false`, origin `fetched`.
  - Models with origin `fetched` that no longer appear upstream are **removed**.
  - Models with origin `user` (manually added in the dialog) are **never
    removed**; if a `user` model no longer appears upstream it is flagged
    `stale: true` and shown with a "not found upstream" marker in the UI.
    Stale `user` models are left indefinitely — the user will notice the
    marker and remove them eventually; the app never prompts for removal.
  - `enabled` state of surviving models is always preserved.
  - If a provider's source fetch fails, its existing list is kept unchanged
    (never blanked) and the failure is reported per provider.
- **FR-A7.** The providers.json model schema is extended from
  `{model_name, enabled, removable}` to
  `{model_name, enabled, origin: "fetched"|"user", stale: bool}`.
  A one-time migration maps existing entries: `removable: true` → `fetched`,
  `removable: false` → `fetched` (curation is replaced by the default-model
  heuristic; nothing is pinned anymore). The UI "removable" behavior becomes:
  `user` models get the trash button; `fetched` models are removed by the
  updater instead.
- **FR-A8. Default free model heuristic.** When generating the bundled
  `providers.json` (CLI mode only, not the in-app update), auto-enable one
  model per provider — the "best available free model":
  1. Candidates with `cost.input == 0 && cost.output == 0` (or OpenRouter
     `:free` suffix), preferring the most recent `release_date`/`last_updated`
     and larger context window as tie-breakers.
  2. If the provider has no zero-cost model but offers a free *tier* (Gemini:
     models.dev costs are paid-tier prices), fall back to a family heuristic:
     newest model whose id/family matches the provider's budget family
     (`flash`/`lite`/`mini`/`small`), e.g. `gemini-flash-latest`.
  3. If neither applies (Anthropic, OpenAI paid-only), enable nothing.

  When both an alias id (e.g. `gemini-flash-latest`) and its concrete
  versioned id are available, **prefer the alias id** — it keeps working
  across provider model rotations so the user updates ids less often.
- **FR-A9.** The CLI command (replacing/refactoring
  `cli/src/update_provider_models.rs`) reads `assets/providers.json`, applies
  FR-A1–A8, and writes it back; used before releases to refresh the bundled
  starting list. Follow the pattern of `update-releases-fallback` (validate
  before writing).

### B. In-app "Update Model Lists" (ModelsDialog.qml)

- **FR-B1.** A button **"Update Model Lists"** at the top of `ModelsDialog.qml`
  runs the shared update procedure against the *user's* current providers
  configuration on a **background thread** (UI stays responsive; pattern: the
  existing bridge thread + signal approach used by `PromptManager`).
- **FR-B2.** While running, the button shows a busy state and is disabled.
  On completion a signal refreshes the dialog's provider/model lists in place.
- **FR-B3.** The in-app update applies the same merge semantics (FR-A6) — adds
  new models, removes obsolete `fetched` models, flags stale `user` models —
  but does **not** apply the default-enable heuristic (FR-A8); the user's
  enabled set is authoritative.
- **FR-B4.** Per-provider fetch failures are summarized non-modally (e.g. a
  status label "Updated 9 providers; Gemini failed: network error"); a total
  failure (models.dev unreachable) shows the error and changes nothing.
- **FR-B5.** All providers supported in the app are updated regardless of
  whether the user has enabled them or entered API keys (the sources are
  keyless).

### C. Global model-usage lists (ModelsDialog.qml, top area)

- **FR-C1.** A new area at the top of `ModelsDialog.qml` holds the global
  options: the **"Fallback sequence"** list, the **"Parallel prompts"**
  list, and the fallback/retry checkboxes.
- **FR-C2.** When the user enables a model in a provider's model list, it is
  appended to **both** lists, enabled by default. When a model is disabled or
  removed, it disappears from both lists. This must hold for **every** removal
  path, including the model-list updater (FR-A6/FR-B3): after an update run
  (in-app or CLI) the lists are reconciled — entries whose `(provider,
  model_name)` no longer exists in the providers configuration are pruned.
  The dialog/bridge sync helpers alone do not cover the updater path, which
  saves the whole providers configuration in one step.
- **FR-C3.** Each list item shows `provider/model_name` and has its own
  enable/disable toggle, so the user controls which enabled models participate
  in sequential fallback and which in parallel requests, independently.
- **FR-C4.** The **Fallback sequence is ordered** and the order is
  authoritative for fallback (the earlier same-provider-first idea is dropped).
  The user can reorder items (up/down buttons; drag optional). New items are
  appended at the end.
- **FR-C5.** The Parallel prompts list is unordered (all enabled items are
  dispatched simultaneously).
- **FR-C6.** Both lists, their per-item toggles and order persist in
  `app_settings` (appdata DB), alongside the existing AI settings keys.
- **FR-C7. Canonical provider names.** The persisted list entries carry the
  provider as a string; the codebase currently has **two spellings** in play
  (serde name `"xAI"` in providers.json / `make_api_request`'s parse vs. the
  Debug form `"XAI"` produced by `format!("{:?}")` in `get_provider_for_model`
  / `is_provider_enabled` / `get_provider_api_key`). The serde name is the
  canonical form. `ProviderName` gets a single canonical string conversion
  (`Display`/`as_str()`), the `{:?}` comparisons are replaced, and any value
  read from legacy settings (e.g. `gloss_word_selection_provider` during
  seeding) is normalized to it.

### D. Fallback and retry engine (Rust, shared)

- **FR-D1.** The QML retry machinery is removed from **both** tabs that carry
  a copy of it: `GlossTab.qml` **and** `PromptsTab.qml` (each has its own
  `is_error_response` / `is_rate_limit_error` string matching,
  `handle_retry_request`, and 5× per-response `retry_count` logic — leaving
  either copy in place would double-retry on top of the Rust engine). A shared
  Rust implementation (in/alongside `bridges/src/prompt_manager.rs`) performs
  fallback and retry for **all** AI request paths: Gloss AI translation, Gloss
  word selection, Prompts chat. The QML tests that exercise the removed
  functions (`tst_GlossTab.qml`, `tst_PromptsTab.qml`) are updated in the same
  change.
- **FR-D2.** Checkbox **"Auto-fallback to next model"** with description:
  *"Auto-fallback and retry with the next model on error such as when rate
  limited."* When enabled and a request fails with a retryable error (see
  FR-E2), the engine sends the request to the **next enabled model in the
  Fallback sequence**.
- **FR-D3.** The existing **"Auto-retry AI Model Requests"** checkbox is kept.
  Semantics after the refactor: when the whole fallback sequence has been
  exhausted without success, and auto-retry is enabled, the engine waits a
  backoff delay and re-runs the sequence — **5 retry rounds with gradual
  backoff (10 s, 20 s, 30 s, 40 s, 50 s)**, constants defined in Rust.
  A description note near the checkboxes reads:
  *"First we auto-fallback, then we re-try the model requests."*
- **FR-D4.** With auto-fallback disabled, a failed request fails immediately
  (auto-retry alone may re-try the same model, preserving a simplified version
  of today's behavior).
- **FR-D5.** Non-retryable errors (invalid API key, bad request, content
  filter) do **not** trigger fallback to a *same-provider* model where the
  error would repeat (invalid key skips the whole provider in the sequence);
  they are reported immediately per FR-F.
- **FR-D6.** The QML side receives progress signals sufficient to display:
  which model is currently being tried, fallback transitions
  ("Rate limited on X, trying Y…"), and final success/failure with the
  responding model's name (existing signals already carry `model_name`).
- **FR-D7.** A sequential request run uses only Fallback-sequence items
  whose toggle is on; a parallel run uses only Parallel-prompts items whose
  toggle is on. If the relevant list has no enabled items, the request fails
  fast with a clear message ("No models enabled for sequential fallback —
  check AI Models settings").
- **FR-D8. Cancellation / total deadline.** Today an abandoned request thread
  lives at most ~180 s (the HTTP client timeout) and QML simply ignores stale
  responses. The engine's worst case is 5 rounds × (N models × 180 s) plus
  150 s of backoff sleeps — an orphaned run could keep making paid API calls
  for a very long time. The engine must therefore support cancellation: a
  generation/cancel token (e.g. an `AtomicUsize` bumped by a
  `cancel_sequential_requests()` qinvokable), checked **before each model
  attempt and after each backoff sleep**; a cancelled run stops silently
  (QML already discards stale responses). The QML cancel paths (Gloss
  `ws_reset` / `ws_cancel_paragraph`, tab/window close) call it. A cancelled
  or superseded run emits no further progress or response signals.

### E. Error classification

- **FR-E1.** Provider request errors must be classified in Rust into a
  structured type carried to QML as JSON, at minimum:
  `{kind, http_status, provider, model, message, raw}` where `kind ∈
  {rate_limited, overloaded, quota_exceeded, auth, invalid_request,
  model_not_found, network, timeout, unknown}`.
- **FR-E2.** Retryable (trigger fallback): `rate_limited` (HTTP 429),
  `overloaded` (503, and Gemini's 500/"model is overloaded" responses),
  `timeout`, `network`, 5xx generally. Non-retryable: `auth` (401/403),
  `invalid_request` (400), `quota_exceeded` when it is a hard monthly/daily
  quota (429 with quota metadata — treat as skip-this-provider),
  `model_not_found` (404 — skip this model, continue sequence).
- **FR-E3.** Classification consults documented provider error statuses
  (e.g. Gemini: 429 RESOURCE_EXHAUSTED, 503 UNAVAILABLE, 500 INTERNAL;
  OpenAI/OpenRouter/Mistral: standard 429/5xx) — via HTTP status where the
  `rig` client surfaces it, plus response-body matching as fallback.

### F. Error message display

- **FR-F1.** For recognized `kind`s the UI shows a human-readable message,
  e.g. "Rate limited by Gemini (gemini-flash-latest). Trying next model…" /
  "Invalid API key for Mistral — check AI Models settings."
- **FR-F2.** For `kind: unknown` the raw response text/JSON is displayed, as
  today (the fallback option).
- **FR-F3.** This applies wherever AI errors surface: Gloss translation
  entries, Word Selection status, Prompts responses.

### G. Feature integration (GlossTab.qml, PromptsTab.qml)

- **FR-G1.** The model picker in the Gloss **"Word Selection..."** dialog
  (`GlossWordSelectionDialog.qml`) is removed; word-selection requests use the
  Fallback sequence (sequential engine). Related settings
  (`word_selection_model`/provider) are dropped/migrated.
- **FR-G2.** `GlossTab.qml` gets a combobox **"AI translation: sequential
  retry / parallel"**, default **sequential**. Sequential: one request walks
  the Fallback sequence and produces one translation. Parallel: one request
  per enabled Parallel-prompts model, results shown side by side (the current
  fan-out shape — but note the retry semantics change: today's QML skips
  retrying rate limits, whereas the Rust same-model retry includes them per
  FR-E2). **Parallel branches never switch models**: the user expects
  results from the specific models they selected. On a retryable error a
  parallel branch auto-retries the *same* model (per the auto-retry setting
  and backoff schedule); otherwise it reports the error for that model.
- **FR-G3.** `PromptsTab.qml` gets the analogous combobox **"Prompts:
  sequential retry / parallel"**, default **sequential**, governing whether the
  next assistant response is requested from one model (with fallback) or from
  all enabled Parallel-prompts models.
- **FR-G4.** Both combobox choices persist in `app_settings` (per feature).
- **FR-G5.** `translation_models` loading in `GlossTab.qml` (currently reads
  all enabled provider models) is repointed at the new global lists.

## 5. Non-Goals (Out of Scope)

1. No new providers (e.g. Groq, Cerebras) — only the 11 already in
   `providers.json`.
2. No automatic *scheduled* model-list updates (only the manual button and the
   CLI); no update-on-startup.
3. No per-model metadata UI (pricing, context size) beyond the model ID and
   the stale marker — the metadata is fetched but only used by the heuristic.
4. No streaming responses, token-cost tracking, or request budgeting.
5. HuggingFace model list auto-update.
6. No change to how API keys are stored/entered.
7. No per-request manual model picker anywhere (that is what the lists
   replace).

## 6. Design Considerations

- The global options area sits above the existing provider SplitView in
  `ModelsDialog.qml`; on mobile-width layouts it must collapse reasonably
  (the dialog already has `is_wide`/`is_tall` adaptive logic). Consider
  collapsible GroupBoxes for the two lists to save vertical space.
- List items: checkbox (toggle) + `Provider / model-id` label + up/down
  buttons (sequence list only).
- The stale marker for user models: subdued warning icon/text
  ("not found upstream"), not blocking.
- Reuse existing dialog patterns: `MessageDialog` for hard failures,
  inline status `Label` for update results.
- New QML components must be added to `qml_files` in `bridges/build.rs`;
  new bridge functions need `qmllint` stubs in
  `assets/qml/com/profoundlabs/simsapa/` (per CLAUDE.md).

## 7. Technical Considerations

- **models.dev findings (verified 2026-07-13):** all supported providers except
  SambaNova are present; entries carry `cost.input/output`, `release_date`,
  `last_updated`, `modalities`, `limit.context`. OpenRouter has 26 zero-cost
  models; **Google has zero cost==0 entries** (free tier is rate-limit-based,
  costs listed are paid-tier) — hence the two-step heuristic in FR-A8.
- The update procedure lives in `backend` (async or blocking `reqwest` —
  note `cli` currently uses blocking, `prompt_manager` uses async; pick one and
  adapt callers). It must not require any API keys (FR-A3).
- In-app background execution follows the existing `PromptManager` pattern:
  spawn thread → `qt_thread().queue(...)` signal on completion.
- The fallback engine needs access to the persisted sequence/toggles from
  `app_settings` — mind the `AppSettings` caches and their refresh hooks
  (see docs/startup-sequence-and-caches.md).
- Error classification depends on what the `rig` provider clients surface;
  where `rig` collapses errors to strings, HTTP status may need to be recovered
  from the error text or by switching those paths to direct `reqwest` calls.
  Audit per provider handler in `prompt_manager.rs`. **Insertion point:** the
  `get_response!` macro (`prompt_manager.rs:100`) stringifies rig errors in its
  `map_err` calls — the classifier must intercept the rig `CompletionError`
  *there*, before stringification (rig's `ProviderError` usually carries the
  response body), not parse the already-formatted string.
- The model add/remove/enable functions currently live in
  `bridges/src/sutta_bridge.rs` (~lines 2749–2812), **not** in
  `backend/src/app_data.rs` (which only has `get/set_providers_json` and the
  settings cache). Moving the mutation + list-sync logic down into
  `app_data.rs` is preferred (testable without Qt, next to the `AppSettings`
  types and cache), with the bridge fns as thin wrappers.
- SuttaBridge already implements `cxx_qt::Threading`
  (`bridges/src/sutta_bridge.rs:671`), and `set_providers_json` already writes
  both the `app_settings_cache` and the DB — so the in-app update's
  "cache refresh after save" comes for free.
- New `app_settings` keys are additive — no DB migration needed; if any new
  table is required instead, remember the dual appdata migration mechanism
  (CLAUDE.md).
- Settings migration: existing users' `removable` flags map per FR-A7; the
  Word Selection saved model (FR-G1) should seed the top of the Fallback
  sequence on first migration so behavior is continuous — but only when
  `gloss_word_selection_enabled` is also true (the settings carry a separate
  enabled flag, and GlossTab already treats a stale/disabled saved model as
  "feature off"), and with the provider name normalized to the canonical
  serde spelling (FR-C7).
- Post-refactor cleanup: the `required property bool ai_models_auto_retry`
  plumbed into the GlossTab/PromptsTab roots (and their instantiation sites)
  becomes dead once retry moves to Rust. The Gloss word-selection status
  message ("Selecting words with X…", `GlossTab.qml` `ws_set_status` call
  sites) names the model *before* the request; under the sequential engine the
  model is only known from the first `sequentialProgress` signal — reword the
  initial message and fill the model name in from progress signals.
- Tests: merge semantics (FR-A6), default heuristic (FR-A8) against a fixture
  models.dev snapshot, error classification (FR-E), fallback ordering (FR-D)
  — pure Rust, no GUI tests.

## 8. Success Metrics

1. A fresh bundled `providers.json` can be regenerated with one CLI command,
   with no manual model ID edits.
2. After entering only a Gemini API key and enabling the provider, AI
   translation works with zero model configuration.
3. "Update Model Lists" completes without freezing the UI and correctly adds
   new / removes obsolete fetched models (verifiable against a live snapshot).
4. With two models enabled in the sequence, forcing a 429 on the first model
   results in a successful response from the second, with the transition
   visible in the UI.
5. Rate limit and invalid-key errors display as plain-language messages; only
   unrecognized errors show raw JSON.

## 9. Open Questions

None — all earlier open questions were resolved with the requester:

1. Alias ids (e.g. `gemini-flash-latest`) are preferred over concrete
   versioned ids (FR-A8).
2. Auto-retry runs 5 rounds with gradual backoff 10 s, 20 s, 30 s, 40 s, 50 s;
   not user-configurable (FR-D3).
3. Parallel branches never switch models; they auto-retry the same model only
   (FR-G2).
4. The "Update Model Lists" button lives only in ModelsDialog (FR-B1).
5. Stale `user`-origin models are left indefinitely, marker only (FR-A6).
