### Specs for 1.0 — auto-lock on pick (and the binding fix it depends on)

- **UI contract:** `DeconstructorSelector` emits `activated(index)` only from `onActivated` (never `onCurrentIndexChanged`), so programmatic index changes do not fire it. The embedder owns `current_index` / `locked` and pushes them back down.
- **Blocker found in review (FR-0e):** the selector violates that contract by writing to its own bound properties — `DeconstructorSelector.qml:56` `root.current_index = index` and `:73` `root.locked = lock_btn.checked`. Both are bound by the embedders (`FulltextResults.qml:207-208`, `WordSummary.qml:265-266`), so each write **destroys the binding**. After one manual lock click the auto-lock in 1.1/1.3 no longer reaches the lock button (stale icon + `checked`); after one manual pick, `reset_deconstructor_state()` can no longer move the ComboBox back to 0. The internal `Binding{}` at `DeconstructorSelector.qml:49` does not help — it feeds `breakdown_combo.currentIndex` *from* the already-stale `root.current_index`. **1.1 must be fixed before the rest of 1.0 has any effect.**
- **Chosen shape:** emit-only. The selector stops writing its own state; the embedder sets its property and the value flows back down through the existing binding. This matches the rule the file already documents at `:13-15` and removes the only place the selector holds authority over state it doesn't own.
- **Reference:** `GlossTab.update_deconstruction_selection()` sets `deconstruction_locked = true` on pick. Note GlossTab is unaffected by the binding bug (it drives the selector through its own model), so it needs no change — but re-check it after 1.1.
- **Independence:** WordSummary is not paginated — `refilter_summaries()` already produces the correct filtered list, so auto-lock is complete there on its own. FulltextResults' auto-lock uses today's client-side filter until Task 4.0 replaces it.
- **Depends on:** nothing.

### Specs for 4.0 — client stops filtering, re-queries instead

- **New division of labour:** the backend sends an already-ordered, already-filtered page; `update_page()` only renders (keeping header dedup, `show_header`, `is_snippet`, `find_query` logic untouched).
- **Re-query on change:** picking a break-down or toggling the lock changes the result set and its length, so the view must request **page 0** again via `new_results_page_fn(0)` rather than re-filtering in place; `page_num` must be reset to 0 first so the paging buttons and label stay consistent. This matches the existing pattern at `FulltextResults.qml:144/157/182` (set `page_num`, then call `new_results_page_fn(root.page_num)`).
- **Page count:** `total_pages` derives from `total_hits`, which is now the filtered DPD total plus the untouched bold/fulltext totals — no QML change needed (FR-5).
- **Visible behaviour change (FR-7a):** today's client filter drops *every* non-header row not in the visible set, which incidentally hides **bold-definition rows** while locked. After 4.1 they are rendered under lock. Intended: the lock chooses a *deconstruction into sub-words*, so it scopes the DPD Lookup stream that shows those sub-words; the bold and fulltext streams query the **complete compound as typed** and never deconstruct, so no break-down choice applies to them. After the sub-word senses, showing where the whole compound is defined in commentary and where it occurs in the texts is what the reader wants next. Consequence (FR-7b): the counter now equals the rows actually reachable, whereas today it over-reports.
- **Section headers are safe:** they are inserted by the bridge's Combined merge (`sutta_bridge.rs:485/491`) *after* the DPD sub-query, so backend filtering can never drop them and the `is_section_header` carve-out in the client filter is not needed once the filter is gone.
- **Empty state:** must appear only when the whole filtered set is empty (`total_hits === 0`), which is now automatic; verify the snippet-exclusion branch of the empty-state text is unaffected.
- **Depends on:** 2.0 and 3.0.

### Specs for 5.0 — Combined path and the other two streams

- **Stream order on a Dictionary page:** regular DPD → bold definitions (`dpd_lookup_with_bold` / `split_page_across_streams`) → Fulltext Match (`fetch_combined_page`, Combined only). Only stream 1 is ordered/filtered.
- **Density:** `split_page_across_streams(regular_total, page_num, page_len)` derives every offset from the regular stream's length, so a filtered length `L` yields dense pages automatically — pure-DPD pages, then one boundary page that tops up from the next stream.
- **Totals:** `filtered_dpd + bold_total (+ fulltext_total)` — a single combined counter (PRD §10 Q3).
- **Hard constraint (FR-9c):** the fulltext sub-query keeps the compound form exactly as typed. `fetch_combined_page` clones `base_params` and swaps only `mode`; do not introduce any component/sub-word query. Do not eagerly materialise the fulltext or bold streams (`vāti` → 6118 fulltext hits, 3.3 s / 3.7 MB).
- **Why streams 2 and 3 are never lock-filtered (FR-7):** the lock selects a *deconstruction of the compound into sub-words*, which is only meaningful for the stream that displays those sub-words. Streams 2 and 3 search the complete compound as typed, so their rows — where the whole compound is defined in commentary, and where it occurs in the texts — are unaffected by which break-down is chosen, and are exactly what a reader wants after the sub-word senses. Any future "helpfully filter these too" refactor is a bug, not an improvement.
- **Depends on:** 2.0, 3.0.
